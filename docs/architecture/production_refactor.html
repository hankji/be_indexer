1. 文档定位

这个仓库不是完整的广告投放引擎，而是“条件匹配核心（Predicate Match Core）”。它的价值在于：将规则表达式和用户特征映射到候选文档集合。它适合做广告定向过滤、规则匹配、商品筛选等阶段，但不负责排序、竞价、预算和频次控制。

当前仓库的关键模块已经体现了合理的核心设计，如：Document、Conjunction、BoolValues、EntriesHolder、IndexerBuilder、KGroupsBEIndex。但如果要达到 Google/Yahoo 级生产环境，需要把它从“算法原型/单机库”升级成“生产级 predicate engine”。

3. 当前性能瓶颈分析

3.1 结构层面：内存对象型 posting list

当前默认 holder 以 map[Term]Entries 为核心，例如 DefaultEntriesHolder 在 entries_holder.go 中使用对象型存储。这个设计容易造成：

  • 大量小对象分配
  • map + slice 造成 GC 压力
  • posting list 扩容带来内存碎片
  • 大规模文档下热点字段的内存占用明显增加

生产级广告系统的常见做法不是追求“泛型对象存储”，而是追求“压缩中的高性能 + 低碎片 + 低 GC”。

3.2 查询层面：缺少 Cost-based Query Planner

在 KGroupsBEIndex.retrieveK 中，查询路径主要做游标排序和归并。算法逻辑正确，但没有按照字段 selectivity 选择执行顺序，也没有对高基数字段做更高效的 range / bitmap 分支处理。

这意味着：

  • 字段顺序不是按候选规模优化
  • 高基数字段容易拖慢查询
  • exclude / multi-value / range 条件的处理不够有成本意识

3.3 构建层面：缺失 segment / snapshot / versioning

现在的增量缓存是 doc-level 的，但真正大规模生产环境中，索引更关注：segment build + versioned snapshot + compaction。当前架构过于“单机内存增量缓存”，缺少版本化索引管理。

3.4 运维层面：缺少 metrics + SLO + workload isolation

生产环境需要 p99/p999、heap profile、GC pause、slow query logging、snapshot health check、index corruption detection 等能力。这些在该仓库中尚不完整。

5. 模块化重构方案

5.1 Predicate Matching Core

目标： 把当前的 KGroupsBEIndex 从“通用匹配器”升级成“生产级查询执行器”。

  • 保留核心表达式语义：Document / Conjunction / BoolValues
  • 新增 planner：按字段选择性决定查询执行顺序
  • 新增 candidate set pipeline
  • 新增 metrics / stats collector

5.2 Storage Layer

将 DefaultEntriesHolder 改成可压缩 posting store：

  • CompressedPostingList
  • RoaringBitmapPostingList
  • RangePostingList
  • StringDictionary

核心要求：低内存、低碎片、高读吞吐、适合多线程查询。

5.3 Segment & Snapshot

把 doc-level cache 升级为 segment-aware cache：

  • SegmentID
  • SchemaVersion
  • SnapshotVersion
  • CompactionVersion

要求：只允许读取已发布快照，避免 stale index。

5.4 Query Runtime

新增以下组件：

  • QueryPlanner
  • FieldSelector
  • CandidateSetBuilder
  • RuntimeReader
  • ShardRouter

让查询在读多写少的情况下使用 immutable snapshot 和 shard-safe access。

6. 代码级重构清单

6.1 be_indexer.go

增加生产环境接口封装：

type IndexStats struct {
    Version        uint64
    FieldCount     int
    PostingCount   int
    CandidateQPS   float64
    AvgLatencyMS   float64
}

type BEIndex interface {
    Retrieve(...)
    RetrieveWithCollector(...)
    GetStats() IndexStats
    GetSnapshotVersion() uint64
    AcquireReader() ReaderHandle
}

6.2 be_indexer_kgroups.go

重点改造：处理 query planner、early exit 和候选构造。

  • 旧：retrieveK 直接遍历 field cursors + sort
  • 新：executeQueryPlan(plan)
  • 新增：selectFieldsByCost(assigns)
  • 新增：canEarlyExit(candidateSet, threshold)

6.3 entries_holder.go

核心改造方向：

  • 旧：map[Term]Entries
  • 新：PostingStore + TermDictionary + CompressedPostingList
  • 新增字段统计：CardinalityHint、AvgPostingSize、Selectivity

6.4 index_builder.go

重构为 pipeline：

  • SchemaRegistry
  • SegmentBuilder
  • Compactor
  • SnapshotPublisher

确保构建过程可被版本化、可回滚和可灰度发布。

6.5 doc_idx_cache.go

升级缓存模型：

type SegmentCacheKey struct {
    SegmentID     string
    SchemaVersion uint64
    BuildVersion  uint64
}

type SnapshotCache struct {
    SegmentID     string
    SchemaVersion uint64
    BuildVersion  uint64
    Data          []byte
}

不再只看 doc id + version，而要考虑 segment 和 schema 版本。

8. 重构路线图

  1. Phase 1：稳定匹配核心
    • 引入 query planner
    • 完善 metrics 和 stats
    • 让读取和构建都能观察性能
  2. Phase 2：压缩与内存优化
    • 改造 default store
    • 采用 compressed postings
    • 添加 bitmap / range store
  3. Phase 3：版本和快照管理
    • segment publish
    • snapshot rollback
    • schema evolution
  4. Phase 4：工业级运行
    • 多线程读取
    • shard / partition
    • canary + monitoring

9. 关键结论

当前仓库最核心的价值在于：把布尔表达式匹配做成了可复用的、可扩展的核心引擎。 它已经具备研究型和工程型基础，但如果要跑到 Google / Yahoo 这样的生产环境，必须从“算法库”升级到“生产级 predicate engine”。

不要继续在单机 map + slice 结构上无限扩张，而要把它演化为：segment-based、compressed、versioned、query-planned、metric-driven 的匹配引擎。
